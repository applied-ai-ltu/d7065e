\section{1. Summary}
%% ============================================================================

This system detects fires in the A-building at LTU and responds autonomously. It is built in two tiers. \textbf{Tier 1} is an edge controller per floor, running on a Raspberry Pi: it reads every room's smoke, CO and temperature, applies a deterministic multi-sensor rule gated by an isolation forest, and releases its own floor's fire doors within one 5\,s tick, with no dependency on a server, a broker or a language model. \textbf{Tier 2} is a server agent: it asks a self-hosted LLM for a verdict on every edge alert, coordinates the other floors, computes evacuation routes, drives the 3D viewer, and stands the building down when readings are clear. A standby controller on a second node takes over a floor within 30\,s if its active controller dies; the server takes over a floor if both controllers are gone; and the whole response still works when the LLM is unreachable.

The building, its 950 rooms on three floors, 124 fire doors, sprinklers and 3D view, is provided by BuildSim. This project provides the physics, the sensor degradation, the two tiers of intelligence and the response around it. The guiding principle is \textbf{life-safety actions at the edge, judgement at the server, graceful degradation everywhere}.

Measured on the homelab cluster during the acceptance run of 3--4 October 2026: ignition to own-floor doors released in 14.7\,s; isolation-forest inference p50 17.8\,ms on the Pi; LLM verdict p50 2.1\,s, p95 3.2\,s; verdict to cross-floor release 25\,ms; standby promotion 30\,s after controller loss. Nine acceptance scenarios pass, including controller failover mid-incident, server takeover of a floor with no controller, LLM outage, broker restart and cold start.

\textbf{Changes since the proposal.} Four design changes were made because the evidence demanded them.
\begin{enumerate}\tightlist
  \item \textbf{From one agent to two tiers.} The proposal had a single server agent polling BuildSim and deciding everything, with the LLM on the critical path. Measured LLM latency (5--7\,s per plan) and the realisation that door release must not depend on a server made the case for a per-floor edge controller that acts first and reports second. The LLM moved off the life-safety path and now only confirms, rejects and coordinates.
  \item \textbf{The LLM returns a verdict, not a plan.} The proposal had the LLM generate the response plan (sprinklers, doors, routes). The plan is now derived deterministically from a verdict \texttt{\{is\_fire, confidence\}}; sprinklers are mechanical in the physics model and never commanded. This halved the verdict latency (5.2\,s to 2.1\,s p50) and removed a class of unsafe plans.
  \item \textbf{GEPA was dropped.} Self-improving prompts added complexity without measurable benefit over a static verdict prompt; the effort went into failover, takeover and the retraining loop instead.
  \item \textbf{Control moved out of Grafana.} The Business Forms plugin proved unsuitable for button control; fire control is a small FastAPI service and Grafana is monitoring only. Scope grew from one room to the whole building once the gateway was parameterised by floor.
\end{enumerate}

\section{2. Use case and building context}
%% ============================================================================

\textbf{The building.} The A-building at LTU is modelled in BuildSim across three floors: level0 (318 rooms, 41 fire doors), level1 (351 rooms, 46 fire doors) and level2 (287 rooms, 37 fire doors). BuildSim is the shared state of the cyber-physical system: it owns the building model, exposes a REST API to read and write equipment state, provides a navigation graph per floor with cross-floor stairwell edges, and streams live state to a 3D web viewer. BuildSim is not modified; it is instrumented. That seam, the building behind BuildSim's API on one side and this project's processes on the other, is what would let the same software drive a real building.

\textbf{How the system connects to BuildSim.} Three things talk to BuildSim, and nothing else touches the building state directly:
\begin{itemize}\tightlist
  \item The \textbf{physics engine and sensor gateway} (inside the server process) read the floor plans, the door graph and the equipment list at start-up, advance the room physics, degrade the readings with realistic faults, and publish them over MQTT. They publish 956 spaces, the 950 rooms plus six combined rooms and corridors that BuildSim lists as equipment but not as rooms.
  \item Each \textbf{edge controller} discovers its floor's fire doors from the equipment list and sets their state directly (\texttt{PUT /api/actuators/\{id\}/state}). This is the only life-safety write path and it does not pass through the server.
  \item The \textbf{server agent} pushes visualisation (effects, alert cards, coverage) and, only for a floor whose controllers are all gone, sets that floor's doors itself.
\end{itemize}

\textbf{Actors.} The \textbf{building operator} watches the 3D viewer and the Grafana dashboards and may start or stop test fires, trigger false alarms and clear the viewer through the control API. \textbf{Building occupants} are modelled by the occupancy simulator and are the reason evacuation routes are computed. Neither actor is on the control path; the loop runs autonomously.

\textbf{The scenario the demo tells.} A fire starts in room A109 on level0. Smoke and CO rise and spread through the door graph to A108, A110 and the corridor. Within three ticks the level0 controller sees smoke above 10\,\%obs/m and CO above 20\,ppm, releases all 41 fire doors on its floor and alerts the server. The server asks the LLM, gets a confirmed verdict two seconds later, releases the doors on level1 and level2, publishes evacuation routes and paints the viewer. Neighbouring rooms are assessed in parallel as their alerts arrive. When the fire is out and readings have been clear for a minute, the server stands each room down; when the last one is clear it re-locks every floor and clears the viewer. If the LLM is down the verdict comes from the same rule the edge used; if the level0 controller dies mid-incident its standby takes over 30\,s later without touching the doors.

\textbf{Why it matters.} Fire is the highest-stakes building automation scenario: late detection kills, false alarms cost evacuations, and a local fire needs a building-wide response. Three concerns drive the requirements: \textbf{act locally and fast}, \textbf{judge with context}, and \textbf{degrade gracefully}. The first is why detection and door release live on the floor; the second is why an LLM reviews every alert; the third is why every component has a documented failure behaviour that was exercised live.

\section{4. Architecture}
%% ============================================================================

\subsection{4.1 Context diagram (C4 Level 1)}

The context view fixes the system boundary. The system reads and commands the building only through BuildSim; the operator watches the viewer and the dashboards and controls through the API; occupants are modelled, not connected; and the LLM inference service and the observability stack are external systems the design must survive without.

\fig[0.85\linewidth]{diagrams/c4_context.pdf}{System context. The Raspberry Pi edge controllers are inside the system boundary; the LLM service and observability are outside it and optional for life-safety behaviour.}{fig:context}

\subsection{4.2 Container diagram (C4 Level 2)}

Each box in Figure~\ref{fig:architecture} is a process or service, placed on the node where it runs. Tier 1 is six edge controllers: an active per floor on the Raspberry Pi and a standby per floor on an amd64 worker, built from the same image with the same resource spec. Tier 2 is the server process, which hosts the physics engine and sensor gateway, the agent, the MQTT-to-database pipeline and the control API. Mosquitto connects the tiers; readings flow down to the controllers, alerts, decisions and heartbeats flow up to the server, commands flow down again. BuildSim is reached by REST from both tiers; the LLM only from Tier 2.

\fig{diagrams/01-architecture.pdf}{Containers and their placement on the k3s cluster. Red edges carry alerts and heartbeats; green edges carry readings and commands; blue edges are REST calls to BuildSim; purple edges are data and model flows.}{fig:architecture}

The closed loop is: the physics engine advances the rooms and publishes degraded readings; the controller on that floor decides; it writes door state into BuildSim; the engine reads the door graph and door states and the next tick reflects them, as does the viewer. The server sits beside this loop, not inside it.

\subsection{4.3 Component diagram (C4 Level 3)}

The two decision components are the ones worth opening. Figure~\ref{fig:decision} shows them side by side, as they run: the edge controller's per-room tick on the left and the server agent's per-alert handling on the right, with the MQTT messages that connect them.

\textbf{Tier 1, per room every 5\,s.} A deterministic multi-sensor rule comes first: smoke $\geq$ 10\,\%obs/m and CO $\geq$ 20\,ppm is a fire, full stop, and the learned model can never veto it. A second rule covers a known-faulty CO sensor (value frozen for 60\,s): then strong smoke alone ($\geq$ 20) confirms. Below those, the isolation forest gates the ambiguous band: a room with smoke $\geq$ 5 that the model flags as anomalous goes to the server as \texttt{possible}; a room with smoke $\geq$ 10 goes to the server even if the model is quiet (safety net). On the first \texttt{fire} on its floor the controller releases every fire door it owns and alerts the server; alerts are rate-limited per room (state change, 1.5× rise, or every 60\,s) so the server is never flooded.

\textbf{Tier 2, per alert, three in parallel.} Alerts are de-duplicated (same room and severity within 60\,s is dropped; a confirmed room is never re-assessed). The agent builds the features the LLM sees: readings and their rates, the list of sensors the edge marked stale, the rooms at risk from spread, and the evacuation route. The LLM returns a verdict. Confidence $\geq$ 0.7 confirms: cross-floor release (once per incident), routes, viewer effects and a red card. Anything else puts the room on a 60\,s watch with an orange card, and readings decide: clear (smoke $<$ 2 and CO $<$ 5 on live sensors) stands the room down, fire-level readings escalate it on the deterministic rule, anything in between keeps watching. A confirmed room is stood down after 60\,s of clear readings. When no room is confirmed or watched anywhere, ALL CLEAR re-locks every floor and clears the viewer. If the LLM is unreachable, the fallback applies the same multi-sensor rule with confidence 0.9 or 0.2.

\section{6. Simulating the sensor values (the physical model)}
%% ============================================================================

BuildSim provides the rooms but not their physics, so the physics engine generates the readings. The aim is enough structure, trends, propagation and genuine responses to the building state, that both tiers react to meaningful data and the loop closes.

\textbf{Temperature} follows a discrete heat balance per room with envelope loss to the outside, fire heat proportional to intensity, occupant heat from the occupancy model, and a sprinkler term. Sprinklers are mechanical: a head activates when the room temperature passes its activation point and then reduces the fire term. They are not commanded by either tier, which matches real buildings and keeps the control path to the doors.

\textbf{Smoke and CO} ramp with fire intensity and decay exponentially when the fire is out. CO decays slower than smoke: after a 45\,s fire the fire room's CO halves roughly every minute, which is why ALL CLEAR follows the stop by about seven minutes. CO does \emph{not} rise during a nuisance event, which is the signal both tiers use to tell a fire from burnt toast.

\textbf{Propagation.} Each tick, a burning room pushes heat, smoke and CO to its neighbours with a factor $1 - d/60$ of the centroid distance $d$. Neighbours are rooms joined by an edge of BuildSim's door graph plus rooms within 30 units; the previous 50-unit radius made A323 a neighbour of A109 across a courtyard, so every A109 fire ``jumped'' to the far wing. Cross-floor spread uses BuildSim's 32 stairwell links at an effective distance of 80.

\textbf{Occupancy} drives the baseline heat load with per-room-type daily profiles and sampled head-counts.

\textbf{Sensor degradation.} The gateway degrades the ground truth with four fault modes: Gaussian noise, response lag, slow drift, and \textbf{stuck} sensors that freeze at a value and recover randomly. The stuck mode turned out to be the most consequential: during acceptance a CO sensor froze at 5.09\,ppm, just above the stand-down threshold, and another froze at 0.00 in the fire room. Both are now handled (Section 7.1), and both are the kind of fault a real building produces.


%% ============================================================================
\section{7. Autonomous services and data pipeline}
%% ============================================================================

\subsection{7.1 The autonomous services}

\textbf{Tier 1: the edge controller} (\texttt{edge/edge\_controller.py}) runs as one process per floor and role. It keeps a short window of readings per sensor per room, tracks when each sensor's value last changed, and every 5\,s evaluates each candidate room as in Figure~\ref{fig:decision}. The isolation forest runs through ONNX Runtime on a six-feature vector (smoke, CO, temperature and their rates); on the Pi 400 this costs 17.8\,ms p50 and 33\,ms p95 per room. On the first \texttt{fire} on its floor the controller releases all of its doors with 16 concurrent PUTs, then alerts the server. It publishes a \texttt{clear} decision when a candidate drops back below threshold so the server's view never freezes on a stale value. It accepts three commands: \texttt{release} and \texttt{lock} for the doors, and \texttt{stand-down} for a room, which it refuses if that room still reads critical. It re-locks only when the floor is clear and it owns the release, or when the server says \texttt{relock} because the controller is new. It skips a door state it already wrote in this process. The standby runs the same code on the same readings with \texttt{acting=false}; after 30\,s without the active's heartbeat it promotes, reports a \texttt{failover}, and demotes when the heartbeat returns.

\textbf{Tier 2: the server agent} (\texttt{src/fds/agent/agent.py}) consumes alerts from a queue with three in flight. Its policy is the right-hand side of Figure~\ref{fig:decision}. Two details matter for safety. First, a doubted alert never undoes the edge: the floor's doors stay released until readings decide. Second, every stand-down carries what the server knows that the controller might not: whether the floor is clear and whether to re-lock. The agent also keeps the per-floor heartbeat table; a floor silent for 30\,s (90\,s after the server's own boot) is taken over: the server subscribes to that floor's readings, applies the threshold rule itself, and actuates its doors directly. The first heartbeat hands the floor back.

\textbf{Why two techniques, and why this split.} The isolation forest learns the boundary of normal from real operation and runs anywhere; the LLM reads context, including the faulty-sensor list, spread risk and the route, and explains itself. Neither is trusted alone: the rule beats the model on the edge, and readings beat the LLM on the server. The LLM's confidence is not a calibrated probability (Section 13), which is why it only gates escalation and stand-down, and why its rejection of an edge-confirmed room is a watch, not a reversal.

\textbf{Degradation.} LLM unreachable: the fallback applies the multi-sensor rule and the strong-smoke-with-stale-CO rule, with confidence 0.9 or 0.2, and the cards say ``fallback mode''. Broker restart: paho reconnects; the controller keeps ticking meanwhile and retries its initial connect with backoff. Server restart: the controllers keep their floors; the next stand-down carries \texttt{relock}. Controller restart or node loss: Section 8.

\textbf{Retraining} (\texttt{fds.models.retrain}, a ClearML task) rebuilds the detector from real operation: per-room 5\,s windows from the readings table, the windows the LLM rejected (weighted ×20), and augmented nuisance events, fitted with contamination 0.02, evaluated against real normal rooms, LLM-confirmed fires, held-out nuisance windows and the deployed model, exported to ONNX and checked for sklearn/ONNX parity. The first retrain on real data replaced a synthetic-trained model that flagged 97\,\% of real normal rooms; the retrain after the acceptance weekend reproduced the deployed model (Section 11), which is the behaviour one wants from a stable loop.

\subsection{7.2 The data pipeline}

Everything the system does leaves a row. The pipeline consumer subscribes to \texttt{building/\#}, \texttt{decisions/\#}, \texttt{alerts/\#} and \texttt{heartbeat/\#} and writes to five hypertables: \texttt{sensor\_readings} (183\,M rows, 18\,GB after eight days), \texttt{edge\_decisions} (every Tier-1 decision, alert and door event with \texttt{if\_ms} and \texttt{if\_anomaly}), \texttt{heartbeats}, \texttt{llm\_overrides} (every Tier-2 verdict, watch, stand-down, takeover and failover with \texttt{llm\_ms}) and \texttt{fire\_events}. Grafana reads them directly; the retraining job reads readings and verdicts, so the LLM's judgements become the labels for the next edge model (Figure~\ref{fig:mlops}).

\fig{diagrams/05-data-mlops.pdf}{Data pipeline and the retraining loop: readings and verdicts flow into TimescaleDB; the retrain task turns verdicts into labels and ships a new ONNX model to every controller.}{fig:mlops}

Measured ingestion is about 410 readings/s sustained with the consumer queue at zero between bursts; a start-up burst of 974 queued messages drained within the minute.

\subsection{8.2 Door lifecycle (state diagram)}

The fire doors of one floor are the state that matters, so the state diagram is theirs rather than a process's (Figure~\ref{fig:doors}). Opening is cheap and safe, so either tier may release. Closing needs agreement: the edge re-locks only when its floor is clear, and refuses a stand-down while a room still reads critical. Because a controller that just started has no memory of what it released, every stand-down carries \texttt{floor\_clear} and \texttt{relock} computed from the server's view, and the ALL CLEAR lock is unconditional for a floor without an own fire. A floor under server takeover follows the same machine with the server in both roles.

\fig{diagrams/04-door-ownership.pdf}{Door states of one floor, who may move between them, and the rules that make the machine survive restarts and failover.}{fig:doors}

Each process also has a small lifecycle: a controller starts, discovers its doors (retrying until BuildSim answers), connects to the broker (retrying with backoff), runs its tick, heartbeat, peer-watch and command loops, and on SIGTERM cancels them and exits 0, which is why pods stop as \texttt{Completed}.

\textbf{What the run found and fixed.} Six defects surfaced during acceptance, all fixed, re-tested and committed during the run:
\begin{enumerate}\tightlist
  \item \textbf{Spread across a courtyard.} A 50-unit centroid radius made A323 a neighbour of A109; every A109 fire lit the far wing. Neighbours are now door-graph edges plus a 30-unit wall radius.
  \item \textbf{A stuck sensor held the stand-down.} \texttt{level0-A108-co} froze at 5.09\,ppm for four minutes, just above the 5.0 clear threshold, keeping three floors open until it recovered. The edge now reports sensors frozen for 60\,s as stale and the stand-down ignores them (never both smoke and CO).
  \item \textbf{The fallback doubted the origin room.} With the LLM down, a reading-scaled confidence put a textbook fire at 0.25; the neighbours were confirmed first and the cross-floor release went out 25\,s late on the wrong room. The fallback now applies the multi-sensor rule with confidence 0.9.
  \item \textbf{A dead CO sensor in the fire room blocked detection.} \texttt{level0-A109-co} stuck at 0.00; the two-sensor rule could never fire and the LLM read ``smoke without CO'' as a nuisance; the floor was handled 11\,s later through the neighbours. Both tiers now use the stale list: strong smoke alone confirms when CO is stale, and the LLM is told which sensors are faulty.
  \item \textbf{Start-order takeover.} Starting the server 45\,s before the controllers produced a takeover of all floors; a 90\,s boot grace fixed it.
  \item \textbf{Duplicate door writes.} The stand-down's re-lock and ALL CLEAR both locked the same doors; a controller now skips a state it already wrote.
\end{enumerate}

\textbf{Honest critique.} The LLM's confidence is not calibrated: in scenario 8 it rejected an edge-confirmed room at confidence 0.00 on borderline readings, and the watch rule had to escalate it on readings a minute later. The design absorbs this, but it means the 0.7 gate is a tuning constant rather than a probability. The ignition-to-release time of 14.7\,s is dominated by the physics ramp and the 5\,s tick, not by inference; a 1\,s tick would cost CPU on the Pi for little benefit. The seven-minute ALL CLEAR is the CO decay model; it is correct behaviour but would feel slow in a demo. Finally, the acceptance run was performed by the author against a simulator the author also wrote; the fault models are plausible but not validated against real sensors.

\section{13. Risks and critical reflection}
%% ============================================================================

\textbf{A server restart in the middle of an incident loses the server's state.} The controllers keep their floors released and nothing is lost on the life-safety side, but the new server does not know an incident is open and no stand-down would ever arrive. During the run this did not bite because ALL CLEAR had already gone out before each redeploy. The mitigation is designed, an edge-side self-clear after a long clear window and a door-state recovery at server boot, and not built. This is the most important known limitation.

\textbf{The LLM's confidence is a number, not a probability.} It works as a gate because readings decide in the end, but a model built to emit calibrated decisions would fit the verdict function better. ``System One'' decision models (Jev, and open-weight equivalents such as OpenJev and Laya) appeared during the project; they return typed answers with probabilities in a few hundred milliseconds. The architecture is already model-agnostic at the verdict boundary, so the natural next step is a hybrid Tier 2: a calibrated decision model for the verdict on the decision path, the LLM kept for reasoning and alert text off it. A fair evaluation would replay the acceptance run's alerts through such a model and compare verdicts and latency with the Qwen results recorded in \texttt{llm\_overrides}.

\textbf{Thresholds are hand-set.} Smoke 10 / CO 20 for fire, 5 for the ambiguous band, 2 / 5 for clear, 60\,s windows, 0.7 confidence. They were chosen from the physics model and tuned on the acceptance run; a real building would need them calibrated per sensor type and installation.

\textbf{The simulator and the system share an author.} Fault models (noise, drift, stuck) are plausible rather than validated, and the physics is optimistic about how cleanly smoke and CO separate a fire from a nuisance. Results are reported against the requirements, not as absolute claims about real buildings.

\textbf{What would be done with more time:}
\begin{itemize}\tightlist
  \item Build the restart-mid-incident mitigation.
  \item The hybrid Tier 2 above, with the offline replay as the evaluation.
  \item Per-sensor calibration profiles and HVAC as a negative feedback term in the physics.
  \item Stairwell-aware cross-floor response: release only the doors on affected routes rather than every door on the other floors.
  \item An operator question channel: ``why was A208 confirmed?'' answered from the stored reasoning.
\end{itemize}
